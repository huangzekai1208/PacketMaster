# PacketMaster V2：RAG、Web 与多 Agent 扩展设计

状态：待评审

关联文档：

- `docs/packetmaster-current-capabilities-and-workflow.md`
- `docs/superpowers/specs/2026-07-20-packetmaster-design.md`

## 1. 背景

PacketMaster V1 已完成单 Agent、CLI、LangGraph 有界取证、FastMCP、speed-analyze 全量流式分析和诊断后持续问答。原始报文留在本地，模型只接收聚合摘要和分页证据。

V2 计划评估三项能力：

1. RAG 故障案例和网络知识库；
2. Web 管理与可视化页面；
3. 多 Agent 分工协作。

这三项能力不能简单并行堆叠。RAG 需要先建立可验证的知识资产和评估集；Web 需要稳定的异步任务与 API 边界；多 Agent 需要在单 Agent 的质量或职责边界出现可测量瓶颈后再引入。否则会增加调用成本、延迟和排障复杂度，却无法证明诊断精度提升。

本设计建议按照“知识层 → 服务与 Web 层 → 有界多 Agent”的顺序演进，每个阶段均保留单 Agent 降级路径。

## 2. 目标

### 2.1 RAG 目标

- 将经过审核的历史故障案例、TCP 协议知识、厂商资料和内部处置手册纳入可检索知识库。
- 根据当前报文的聚合特征、候选原因和用户问题检索相关知识，而不是仅根据自然语言关键词检索。
- 每个知识结论提供来源、版本、适用条件和引用位置。
- 明确区分报文直接证据、知识库经验和报文外假设。
- 建立离线评估集，证明检索能够改善原因覆盖率、解释质量或处置建议准确性。

### 2.2 Web 目标

- 提供任务创建、运行状态、历史任务、诊断报告、证据查看和持续问答界面。
- 支持几百 MB 到数 GB 报文的本地路径分析，并为远程部署提供可选的分片续传能力。
- 将长时间报文分析放入后台任务，不阻塞 HTTP 请求或浏览器页面。
- 可视化吞吐量、RTT、重传、窗口、流排名、异常区间和关键证据。
- 保持 CLI 和 Web 共享同一诊断服务、领域模型、LangGraph 和 MCP 工具。

### 2.3 多 Agent 目标

- 将报文证据分析、知识检索和独立复核拆分为边界明确的语义角色。
- 支持在基础分析完成后并行形成“报文证据视角”和“知识经验视角”。
- 使用独立验证角色检查候选原因的证据充分性、引用有效性和矛盾点。
- 所有 Agent 使用结构化契约、调用预算和循环上限，禁止自由无限协作。
- 多 Agent 失败时能够回退到现有单 Agent 诊断流程。

## 3. 非目标

V2 不包含：

- 将原始 pcap/pcapng 或 Payload 写入向量数据库；
- 用知识库命中结果替代报文直接证据；
- 允许 Agent 自动修改操作系统、服务器或网络设备配置；
- 允许 Agent 自由创建其他 Agent 或无限互相对话；
- 第一阶段建设复杂的多租户 SaaS、计费和组织管理；
- 在浏览器内解析数 GB 报文；
- 用 Web 前端重新实现 TShark、speed-analyze 或诊断算法；
- 未经审核就将模型回答自动写入正式知识库。

## 4. 核心设计原则

### 4.1 证据优先级

诊断结论必须遵循以下优先级：

1. 当前报文的直接证据；
2. 当前报文全量聚合形成的间接判断；
3. 与当前特征匹配且经过审核的历史案例；
4. 标准、厂商文档和内部知识；
5. 无法在报文中验证的外部因素假设。

低优先级信息不能覆盖高优先级证据。若历史案例与当前报文冲突，报告必须保留冲突并以当前报文为准。

### 4.2 确定性处理不 Agent 化

以下工作继续由确定性代码完成：

- 文件校验、哈希、磁盘预算和生命周期管理；
- TShark 调用、报文筛选、字段提取和全量聚合；
- SQLite 证据索引和分页查询；
- 权限校验、敏感字段过滤和 API Schema 校验；
- 任务状态迁移、超时、取消和报告落盘；
- 图表数据计算和报告中的确定性指标。

Agent 只处理需要语义判断的假设生成、知识关联、证据解释、反向验证和自然语言问答。

### 4.3 单一诊断核心

CLI、Web 和未来其他入口必须调用同一个应用服务，禁止复制诊断逻辑。诊断服务仍以 `analysis_id` 作为任务和证据边界。

### 4.4 有界自主性

所有模型和 Agent 调用必须有：

- 输入 Schema；
- 输出 Schema；
- 工具白名单；
- 最大轮数；
- 最大请求数；
- 超时和取消；
- Token 与费用预算；
- 失败降级路径。

## 5. 建议总体架构

```text
CLI                         React Web
 |                              |
 +--------------+---------------+
                |
                v
        PacketMaster API / 应用服务
                |
       +--------+---------+
       |                  |
       v                  v
异步任务管理器       对话与报告查询
       |
       v
确定性诊断协调器（LangGraph）
       |
       +----> FastMCP ----> speed-analyze / TShark / SQLite 证据
       |
       +----> RAG Retrieval Service
       |
       +----> 单 Agent 或有界多 Agent 语义层
       |
       v
Artifact Store + Task Store + Knowledge Store
```

建议技术选择：

| 层 | 建议 |
| --- | --- |
| Web 前端 | React、TypeScript、Vite |
| Python API | FastAPI |
| 实时进度 | Server-Sent Events，必要时再增加 WebSocket |
| 后台任务 | V2 初期使用独立本地 Worker 和持久任务表；扩展部署再接 Redis 队列 |
| 任务元数据 | 单机先使用 SQLite；多用户或多节点时迁移 PostgreSQL |
| 知识元数据和审核状态 | 单机先使用 SQLite；服务化后使用 PostgreSQL |
| 向量检索 | 通过 `KnowledgeStore` 抽象接入；首版建议 Qdrant Local，服务化后切换 Qdrant Server |
| 关键词检索 | SQLite FTS5 或服务端全文索引，与向量检索组合 |
| 报文与分析产物 | 本地文件系统；后续可通过 ArtifactStore 接口接入对象存储 |

首版 Web 仍以 Windows 单机或内网单节点部署为主，不应在尚未验证需求前引入 Kubernetes 和复杂微服务。

## 6. RAG 知识层设计

### 6.1 知识来源

知识库分为四类，必须保留类型和权威等级：

| 类型 | 示例 | 默认权威等级 |
| --- | --- | --- |
| 标准与协议知识 | RFC、标准组织资料、TCP 算法说明 | 高 |
| 厂商知识 | 操作系统、网卡、负载均衡、测速工具文档 | 中高 |
| 内部处置知识 | 经审核的操作手册、排查流程和环境约束 | 中高 |
| 历史故障案例 | 已关闭工单、人工确认的 PacketMaster 报告 | 取决于审核状态 |

未经审核的模型回答、临时聊天记录和未确认诊断不得进入正式检索集合。它们可以进入隔离的“待审核区”，但默认不可被生产诊断召回。

### 6.2 故障案例结构

历史案例不能只保存一段最终结论。每个案例至少包含：

- `case_id` 和版本；
- 标题、来源、创建时间和审核人；
- 适用环境，如操作系统、链路类型、测速工具和网络拓扑；
- 标准带宽、实际带宽、方向和达标率；
- 脱敏后的全局 TCP 特征；
- 脱敏后的每流和时间区间异常摘要；
- 已确认主因和候选原因；
- 支持证据、反向证据和不可观测因素；
- 最终处置动作和处置结果；
- 置信等级和审核状态；
- 与原报告的本地引用，不包含原始报文和绝对路径。

案例特征必须来自稳定的结构化字段。模型生成的自由文本仅作为补充描述，不能作为唯一检索依据。

### 6.3 文档切分

不同知识类型使用不同切分规则：

- RFC 和厂商文档按章节、标题和语义段落切分；
- 内部手册按“现象、前置条件、检查方法、判断标准、处置动作、风险”切分；
- 故障案例按案例整体保留结构，并为现象、证据、原因和处置建立子文档；
- 表格和命令不能与其标题、前置条件和风险说明分离；
- 每个切片保留父文档、章节、版本、来源、适用范围和审核状态。

不采用固定字符数粗暴切分作为唯一策略。

### 6.4 检索输入

检索查询由确定性的 `KnowledgeQueryBuilder` 从当前任务构建，输入只包括：

- 目标方向和带宽达标率区间；
- 全局 TCP 指标；
- 异常流和异常时间区间摘要；
- 当前候选原因及其缺失证据；
- 用户当前问题；
- 用户显式提供的环境标签。

原始报文、Payload、完整逐包数据、本地绝对路径和 API Key 不得进入检索查询或向量库。

### 6.5 混合检索流程

```text
结构化诊断上下文
  |
  v
元数据过滤（方向、环境、知识类型、审核状态、版本）
  |
  +-- 关键词/BM25 检索
  |
  +-- 向量语义检索
  |
  v
结果合并与去重
  |
  v
重排（相关性、权威等级、适用条件、时效性）
  |
  v
多样性控制与引用打包
```

默认只召回审核通过且当前有效的知识。检索结果必须有数量和字节上限，避免知识上下文挤占报文证据上下文。

### 6.6 知识引用契约

每个进入模型的知识片段必须包含：

- `knowledge_id`；
- 标题和知识类型；
- 来源和版本；
- 章节或案例引用位置；
- 审核状态和权威等级；
- 适用条件；
- 有界正文；
- 检索分数和重排分数。

模型输出中凡是使用知识库形成的判断，必须引用 `knowledge_id`。引用不存在、版本失效或适用条件不匹配时，验证节点应拒绝该知识结论。

### 6.7 知识入库与审核

知识生命周期：

```text
导入 -> 格式解析 -> 脱敏 -> 切分 -> 元数据补全
     -> 待审核 -> 审核通过 -> 建索引 -> 可检索
     -> 更新/过期 -> 重建索引或停用
```

历史诊断案例只有在人工确认主因和处置结果后才能进入正式知识库。知识更新必须产生新版本，已有报告继续引用原版本，保证可追溯性。

### 6.8 RAG 评估

在上线前建立不少于 50 个脱敏问题/案例的评估集，至少评估：

- Recall@5：正确知识是否进入前 5 个结果；
- MRR：正确知识的平均排名；
- 引用准确率：回答引用是否真实支持对应陈述；
- 适用条件准确率：是否误用不同操作系统、设备或协议版本的知识；
- 诊断原因覆盖率：与不使用 RAG 的单 Agent 相比是否提升；
- 幻觉率：没有来源支持的知识性陈述比例；
- 延迟和 Token 增量。

RAG 上线门槛建议：Recall@5 不低于 85%，引用准确率不低于 95%，且不能降低报文证据一致性。

## 7. Web 管理与可视化设计

### 7.1 用户角色和部署模式

首版支持两种部署模式：

1. 本机模式：PacketMaster、浏览器和报文位于同一 Windows 主机，优先使用本地路径注册；
2. 内网服务模式：浏览器与分析服务分离，使用分片续传将报文上传到受控暂存区。

本机模式默认只监听 `127.0.0.1`。一旦监听非本机地址，必须启用身份认证、授权、TLS 或可信反向代理，不能沿用无认证模式。

### 7.2 页面范围

Web 首版包含：

- 任务列表：状态、文件名、方向、标准/实际带宽、开始时间和耗时；
- 新建分析：选择本地文件或注册服务端路径，填写带宽和方向；
- 任务详情：当前阶段、进度、已处理报文数、耗时、取消和重试；
- 报告视图：主因、候选原因、置信度、限制、排查步骤和优化建议；
- 流视图：各 TCP 流吞吐、RTT、重传、窗口和异常排名；
- 时间视图：吞吐、RTT、重传和窗口随时间变化；
- 证据视图：按流、时间区间和证据类型分页查看允许字段；
- 对话区：围绕当前 `analysis_id` 追问，并展示证据引用和知识引用；
- 知识管理：导入、审核、版本、停用和评估状态，默认仅管理员可见。

### 7.3 大报文输入

数 GB 报文不应通过普通单请求上传。

本机模式：

- 前端只提交用户选择后由后端确认的本地文件句柄或受控路径引用；
- 后端必须校验路径位于允许目录，禁止任意路径遍历；
- 浏览器不能直接获得服务器绝对路径。

内网服务模式：

- 使用分片上传、断点续传和服务端最终哈希校验；
- 上传状态与分析任务状态分离；
- 只有上传完成并校验成功后才能创建分析任务；
- 暂存目录必须配置配额、有效期和清理策略；
- 文件名只用于展示，存储位置使用服务端生成的对象 ID；
- 不在数据库、日志或事件流中保存报文内容。

### 7.4 后台任务模型

任务状态建议固定为：

```text
created -> staging -> queued -> validating -> analyzing
        -> reasoning -> verifying -> reporting -> completed
```

终止状态包括：`completed`、`partial`、`failed` 和 `cancelled`。

状态迁移由后台 Worker 控制，HTTP API 不能直接伪造状态。每次迁移记录时间、阶段、进度、错误码和恢复建议，不记录 Payload、完整模型消息或绝对路径。

### 7.5 API 边界

建议提供以下资源，不在路由层实现诊断逻辑：

| 资源 | 职责 |
| --- | --- |
| `/api/analyses` | 创建和列出分析任务 |
| `/api/analyses/{id}` | 查询状态和基础元数据 |
| `/api/analyses/{id}/cancel` | 请求安全取消 |
| `/api/analyses/{id}/report` | 获取结构化报告 |
| `/api/analyses/{id}/evidence` | 查询分页证据 |
| `/api/analyses/{id}/chat` | 提交报告追问 |
| `/api/analyses/{id}/events` | 通过 SSE 获取阶段和进度事件 |
| `/api/uploads` | 创建和管理分片上传 |
| `/api/knowledge` | 管理知识文档、版本和审核状态 |

所有请求和响应继续使用 Pydantic Schema。证据查询复用现有字段白名单、分页、大小限制和 `analysis_id` 校验。

### 7.6 可视化原则

- 图表使用聚合数据，不从浏览器请求完整逐包数据；
- 时间序列默认降采样，但异常区间、截断信息和覆盖范围必须可见；
- 流表支持排序、筛选和比较，不使用大量装饰性卡片；
- 报告结论旁同时展示证据强度、覆盖完整性和知识引用；
- 用户可以从候选原因跳转到对应流、时间区间和证据页；
- 图表和文本必须明确单位，避免 Mbps、MB/s 和字节混淆；
- Web 只展示脱敏文件名，不向普通用户展示服务端绝对路径。

### 7.7 CLI 兼容

Web 接入后，以下行为保持不变：

- `packetmaster diagnose` 和 `packetmaster chat` 继续可用；
- CLI 和 Web 生成相同的 `DiagnosticReport`；
- CLI 不依赖前端构建产物；
- Web API 调用应用服务，不通过启动 CLI 子进程完成诊断。

## 8. 多 Agent 协作设计

### 8.1 引入条件

多 Agent 不应仅因为技术上可实现就启用。至少满足一个条件后再进入生产：

- RAG 和非 RAG 信息经常需要独立推理并出现上下文竞争；
- 单 Agent 在评估集中持续遗漏重要原因；
- 独立验证能够显著降低无证据结论或错误引用；
- 并行语义分析能够在可接受成本内降低总延迟；
- 角色拆分后的质量提升能够通过固定评估集复现。

若多 Agent 相比单 Agent 没有显著提升，应继续使用单 Agent。

### 8.2 角色划分

建议采用一个确定性协调器和三个语义 Agent：

| 角色 | 输入 | 输出 | 可用工具 |
| --- | --- | --- | --- |
| Evidence Analyst | 报文聚合上下文和分页证据 | 基于当前报文的候选原因、证据缺口 | 只读 MCP 证据查询 |
| Knowledge Researcher | 结构化异常特征和候选原因 | 相关知识、相似案例、适用条件和引用 | 只读 RAG 检索 |
| Verification Agent | 两类候选结果及引用 | 支持、反向证据、冲突、置信度和最终候选集合 | 有界 MCP 与 RAG 复核 |
| Coordinator | 结构化状态 | 调度、预算、合并、降级和结束 | 不进行自由语义推理 |

最终报告仍由确定性 Report Builder 生成。若需要自然语言润色，可以增加受约束的表达步骤，但不得改变原因、证据、置信度和引用。

### 8.3 协作流程

```text
基础报文分析完成
       |
       +--------------------+
       |                    |
       v                    v
Evidence Analyst     Knowledge Researcher
       |                    |
       +---------+----------+
                 |
                 v
         Verification Agent
                 |
          +------+------+
          |             |
      证据充分       需要有限补证
          |             |
          |       MCP/RAG 复核一次
          |             |
          +------+------+
                 |
                 v
       确定性报告生成与持久化
```

Evidence Analyst 与 Knowledge Researcher 可以并行运行。Verification Agent 不接受两者的隐藏推理，只接受结构化候选原因、证据引用、知识引用、缺失项和限制。

### 8.4 共享状态契约

Agent 之间不传递自由聊天消息，统一通过结构化对象交换：

- `analysis_id`；
- `candidate_id`；
- 原因描述和可观测性；
- 支持与反向报文证据引用；
- 知识引用及适用条件；
- 缺失证据；
- 建议的有界查询；
- 置信度和置信度依据；
- 限制和冲突。

每个引用必须能够由协调器重新解析和校验。Agent 不能通过文本声称某条证据存在。

### 8.5 冲突处理

当角色结论冲突时：

1. 先检查报文覆盖是否完整；
2. 校验证据和知识引用是否真实存在；
3. 检查知识的适用环境和版本；
4. 以当前报文直接证据为最高优先级；
5. 无法消解时保留多个候选原因和冲突说明，不强行选择唯一主因；
6. 报文外因素只能标记为待外部验证，不能伪装成已确认原因。

### 8.6 预算和降级

建议初始预算：

- 每个语义 Agent 最多 1 次初始调用；
- Verification Agent 最多发起 1 轮补充取证；
- 每个任务设置总模型调用数、总 Token、总费用和总时长上限；
- 任一 Agent 超时不阻止已有结果进入验证；
- RAG 不可用时退化为报文证据单 Agent；
- 多 Agent 协调失败时回退到 V1 诊断图；
- 降级信息必须写入报告限制和 trace。

## 9. 统一 V2 工作流程

```text
创建任务
  |
  v
文件注册/上传完成 -> 参数校验 -> 用户确认
  |
  v
后台 Worker 执行 speed-analyze 全量分析
  |
  v
Context Builder 生成有界报文上下文
  |
  +-----------------------------+
  |                             |
  v                             v
报文证据候选原因             RAG 混合检索
  |                             |
  +-------------+---------------+
                |
                v
      单 Agent 或多 Agent 证据复核
                |
                v
       确定性报告 + 引用 + trace
                |
       +--------+---------+
       |                  |
       v                  v
   CLI 输出          Web 可视化与问答
```

## 10. 数据和持久化边界

建议将数据分为四个存储域：

1. Task Store：任务参数、状态、阶段、错误码和时间；
2. Artifact Store：原始报文引用、筛选报文、统计、SQLite 证据和报告；
3. Knowledge Store：知识文档、切片、向量、审核状态和版本；
4. Conversation Store：有界对话、引用和当前 `analysis_id`。

四个存储域使用不同的生命周期和权限。删除任务不能误删共享知识；停用知识不能修改已完成报告中的历史引用；删除上传报文前必须检查是否存在运行中的分析任务。

## 11. 安全与隐私

### 11.1 保持 V1 边界

以下内容继续禁止进入模型、RAG 查询、浏览器事件和普通日志：

- 原始报文二进制和 Payload；
- 完整逐包数据；
- API Key、Token 和密码；
- 服务端本地绝对路径；
- 未经字段白名单过滤的日志和工具输出。

### 11.2 Web 安全

- 服务端路径必须通过受控目录和路径归一化校验；
- 上传文件使用服务端对象 ID，不信任客户端文件名；
- 限制上传大小、并发数、分片数和暂存时间；
- 防止路径遍历、符号链接逃逸和跨 analysis_id 访问；
- 网络模式必须认证，知识审核和删除操作需要更高权限；
- API 错误不得回显模型密钥、内部堆栈和绝对路径；
- SSE 和下载链接必须绑定用户和任务权限。

### 11.3 RAG 安全

- 入库前执行来源校验、脱敏和 Prompt 注入扫描；
- 知识正文中的指令只视为数据，不能改变系统 Prompt 或工具权限；
- 外部文档默认进入待审核区；
- 记录知识版本、审核人和索引时间；
- 检索结果再次经过敏感字段过滤后才能进入模型。

## 12. 可观测性

V2 trace 在 V1 节点信息基础上增加：

- 任务状态迁移和耗时；
- RAG 检索数量、知识 ID、版本和分数，不记录完整知识正文；
- 各 Agent 的角色、状态、耗时、Token、错误码和降级原因；
- MCP 请求类型、数量、分页和响应大小；
- Web 请求 ID、任务 ID 和 analysis_id 的关联；
- 上传分片进度、校验状态和清理事件。

不得记录隐藏推理、完整模型消息、用户报文内容和密钥。

## 13. 性能和容量要求

- Web 创建任务接口应在 1 秒内返回任务 ID，不等待报文分析完成；
- 进度事件在状态变化后 2 秒内到达前端；
- Web 页面不加载完整 interval 或证据集合，默认分页和降采样；
- 单次 RAG 最终进入模型的知识片段建议不超过 8 条和 32 KB；
- RAG 检索 P95 目标不超过 2 秒，不包含模型生成时间；
- 多 Agent 总调用预算不得超过单 Agent 基线的 3 倍，除非评估证明收益；
- 大报文分析仍遵守现有内存和磁盘发布门禁；
- 同一报文的重复任务可基于输入哈希复用确定性基础分析，但必须重新校验参数、方向和产物完整性。

## 14. 测试策略

### 14.1 RAG 测试

- 知识解析、切分、版本、审核和停用测试；
- 关键词、向量、元数据过滤、合并和重排测试；
- 无权限知识和待审核知识不可召回；
- Prompt 注入知识不能改变 Agent 行为；
- 引用不存在、过期或不适用时验证失败；
- 固定评估集的 Recall@K、MRR、引用准确率和诊断覆盖率门禁。

### 14.2 Web 测试

- API Schema、认证、授权和跨 analysis_id 隔离测试；
- 分片上传、断点续传、哈希失败、配额和清理测试；
- 后台任务状态机、取消、重试、崩溃恢复和幂等测试；
- SSE 断线重连和事件顺序测试；
- React 桌面和常用笔记本视口的端到端测试；
- 数 GB 报文不进入浏览器内存和 API JSON 的验证；
- Windows 正式门禁和 macOS 兼容门禁。

### 14.3 多 Agent 测试

- 每个角色只能使用授权工具；
- 跨 analysis_id 证据和伪造引用被拒绝；
- Agent 超时、无输出和冲突时可降级；
- 并行结果顺序变化不影响最终确定性合并；
- 固定案例上与 V1 单 Agent 进行盲测对比；
- 统计质量、延迟、Token 和费用，不只比较主观表达效果。

## 15. 分阶段交付建议

### 阶段 A：知识资产与 RAG 评估

- 定义知识和案例 Schema；
- 建立导入、脱敏、审核、版本和停用流程；
- 实现 KnowledgeStore 与混合检索；
- 建立固定评估集和无 RAG 基线；
- 仅在 CLI 或离线测试中展示知识引用，不改变主诊断流程。

验收后再将 RAG 接入候选原因生成和问答。

### 阶段 B：应用服务与 Web 工作台

- 从 CLI 中提取稳定的应用服务；
- 实现任务存储、后台 Worker、状态机和 SSE；
- 实现 React 任务列表、任务详情、报告、图表、证据和对话；
- 先支持本地路径模式，再增加分片上传；
- 保持 CLI 回归兼容。

### 阶段 C：有界多 Agent 实验

- 在离线评估环境实现 Evidence Analyst、Knowledge Researcher 和 Verification Agent；
- 与 V1 单 Agent 进行质量、成本和延迟对比；
- 只有达到明确质量门槛才在生产启用；
- 默认保留单 Agent 开关和自动降级。

### 阶段 D：生产加固

- 身份认证和角色权限；
- PostgreSQL、Qdrant Server 或 Redis 等服务化存储；
- 并发、配额、备份、恢复和审计；
- Windows 服务安装、升级和回滚；
- 大报文、多任务和长时间运行门禁。

## 16. 验收标准

V2 设计整体完成需满足：

1. RAG 只检索审核通过的知识，每个知识性结论都能定位来源和版本；
2. RAG 不向模型或向量库暴露原始报文、Payload、密钥和绝对路径；
3. Web 能创建、观察、取消和查看长时间分析任务，浏览器不承担报文解析；
4. Web、CLI 使用同一诊断服务和报告契约；
5. 时间序列、流和证据均按有界数据展示，不一次加载完整逐包集合；
6. 多 Agent 只交换结构化状态，工具、轮次和成本均有上限；
7. 多 Agent 失败能够回退到单 Agent，不导致基础分析结果丢失；
8. Windows 通过正式发布门禁，macOS 通过开发兼容门禁；
9. 固定评估集证明 RAG 或多 Agent 相对 V1 有可重复的质量提升；
10. 所有最终原因仍以当前报文证据和覆盖完整性为核心。

## 17. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 历史案例本身结论错误 | RAG 放大错误经验 | 人工审核、版本、停用、引用和离线评估 |
| 相似案例环境不同 | 误用处置建议 | 强制环境元数据过滤和适用条件校验 |
| 多 Agent 互相强化幻觉 | 结论看似一致但无证据 | 独立验证、引用重查、报文证据优先 |
| 多 Agent 成本和延迟过高 | 用户体验和预算不可控 | 调用预算、并行执行、单 Agent 回退 |
| 数 GB 浏览器上传不稳定 | 任务失败和磁盘占满 | 本地路径优先、分片续传、配额和哈希 |
| Web 暴露本地文件系统 | 数据泄漏 | 受控目录、路径引用、权限和脱敏 |
| 前后端复制诊断逻辑 | 行为漂移 | 单一应用服务和共享领域契约 |
| 过早服务化 | 运维复杂度超过收益 | Windows 单节点起步，按容量门槛扩展 |

## 18. 待评审决策

进入实施计划前需要确认：

1. Web 首版只支持本机模式，还是同时支持内网远程上传；
2. 首批可用于 RAG 的知识来源和人工审核负责人；
3. 是否允许使用云端 Embedding，还是要求知识向量化完全本地运行；
4. Web 是否需要从首版支持多用户登录和权限；
5. 多 Agent 的上线质量门槛和可接受模型调用成本；
6. 历史诊断案例是否允许自动进入待审核区；
7. 生产环境是否允许 Docker，决定 Qdrant Server、PostgreSQL 和 Redis 的部署方式。

在上述决策确认前，可以开展知识 Schema、RAG 离线评估集和应用服务边界设计，但不应直接开始 Web 全量开发或生产多 Agent 编排。

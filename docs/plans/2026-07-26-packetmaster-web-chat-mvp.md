# PacketMaster Web 对话界面 MVP 实施计划

日期：2026-07-26

状态：待评审

依据：`docs/specs/2026-07-26-packetmaster-web-chat-mvp-design.md`

## 1. 已确认决策

- MVP 使用输入或粘贴本机报文路径，不提供浏览器报文上传。
- Web 服务默认且仅监听 `127.0.0.1`，MVP 不提供登录系统。
- 后台分析默认单 Worker、单任务并发。
- 使用 SQLite WAL 保存会话、消息、报文引用、任务和进度事件。
- 前端使用 React、TypeScript、Vite、TanStack Query、ECharts 和 Lucide React。
- 后端使用 FastAPI、Pydantic 和 SSE。
- Tauri 原生文件选择放在 MVP 之后。
- TCP 流视图展示完整流列表，但必须使用服务端分页、筛选和排序。
- CLI 与 Web 必须共享同一诊断应用服务和报告契约。
- 在 spec 和 plan 均确认后再开始功能代码编写。

## 2. 全局实施约束

- 默认分析方向保持 `download`，只有用户明确指定才使用 `upload` 或 `both`。
- 原始报文、Payload、完整逐包数据、完整日志、API Key 和本地绝对路径不得进入模型上下文。
- 浏览器后续请求只使用 `capture_id`，不得持久化真实绝对路径。
- 数 GB 报文由现有本地流式流水线处理，不通过 API JSON 或浏览器内存流转。
- 前端不得复制诊断规则、带宽换算、证据过滤和任务状态迁移逻辑。
- FastAPI 路由不得直接调用 Typer，也不得在请求协程中执行完整报文分析。
- Worker、TShark 子进程和取消逻辑必须兼容 Windows 与 macOS。
- 每个任务先编写或更新测试，再实现对应行为。
- 每个阶段运行相关测试和 Ruff；前端阶段运行 TypeScript、Lint、组件测试和构建。
- 保留用户无关修改，不提交 `.DS_Store`、本地报文、分析产物、构建目录和编辑器配置。
- Git 提交信息使用中文。

## 3. 阶段一：建立共享应用服务

### 任务 1：提取界面无关的诊断应用服务

目标：将当前 CLI 中的诊断执行逻辑迁移到独立应用服务，作为 CLI 和 Web 的共同入口。

工作内容：

- 定义诊断请求、执行结果、进度事件和取消信号的应用层契约。
- 将 LangGraph、FastMCP Client、RealAnalyzerAdapter、Context Builder 和报告持久化编排迁移到应用服务。
- 应用服务不依赖 Typer、FastAPI、React 或浏览器概念。
- CLI 改为调用应用服务，保持现有参数、输出、退出码、报告和进度行为。
- 保留部分完成和失败降级语义。

验收标准：

- `packetmaster diagnose` 和 `packetmaster chat` 行为不变。
- 同一输入在重构前后生成等价 `DiagnosticReport`。
- 应用服务可以注入模型、MCP、进度和取消依赖进行测试。
- 现有非性能测试全部通过。

建议提交：`refactor: 提取共享诊断应用服务`

### 任务 2：定义 Web 领域契约和稳定错误模型

目标：固定前后端共享的会话、报文、任务、事件、报告和错误 Schema。

工作内容：

- 定义会话、消息、报文引用、待确认意图、分析任务和事件模型。
- 固定任务状态、消息类型和 SSE 事件类型。
- 定义统一成功响应和错误响应。
- 所有错误提供稳定错误码、中文消息、是否可恢复和建议动作。
- 明确哪些字段仅存在后端，哪些字段允许返回前端。
- 增加敏感字段序列化测试。

验收标准：

- 非法状态、非法消息类型和额外字段在服务边界被拒绝。
- 任意前端响应不包含 API Key、Payload 和本地绝对路径。
- OpenAPI 能完整表达 MVP API 契约。

建议提交：`feat: 定义Web领域契约与错误模型`

## 4. 阶段二：建立本地持久化与报文注册

### 任务 3：实现 SQLite 数据库和迁移机制

目标：持久保存会话、消息、报文引用、任务状态、事件和诊断后问答。

工作内容：

- 建立 SQLite WAL 数据库连接和事务边界。
- 建立版本化迁移机制，禁止依赖启动时临时猜测表结构。
- 实现 sessions、messages、captures、analyses、analysis_events 和 chat_turns 数据表。
- 为状态、时间、session_id、analysis_id 和 event_id 建立索引。
- 定义任务、会话和事件 Repository 接口。
- 实现分页、排序、幂等写入和并发访问测试。

验收标准：

- 服务重启后能够恢复会话、消息和任务状态。
- SQLite 写入不会阻塞 SSE 长连接和只读查询。
- 迁移可重复执行，不破坏已有数据。
- 数据库不保存报文二进制、Payload、API Key 和完整模型消息。

建议提交：`feat: 增加Web本地持久化`

### 任务 4：实现安全的本机报文注册

目标：将真实路径转换为仅在后端解析的 `capture_id`。

工作内容：

- 配置允许读取报文的目录列表。
- 校验路径长度、绝对路径、文件存在、普通文件、后缀、可读性和大小。
- 防止路径遍历、符号链接逃逸和目录注册。
- 保存真实路径、脱敏文件名、大小、修改时间和可选文件指纹。
- 返回 `capture_id`、文件名、大小和注册状态。
- 提供最近使用报文列表，不递归扫描整个磁盘。
- 删除报文引用时不删除用户原文件。

验收标准：

- Windows 盘符、反斜杠、空格和中文路径可注册。
- macOS 路径和配置允许目录可注册。
- 非允许目录、符号链接逃逸和非法后缀被拒绝。
- API 响应、日志和 SSE 不出现真实绝对路径。

建议提交：`feat: 实现本机报文安全注册`

## 5. 阶段三：实现后台任务和进度事件

### 任务 5：实现分析任务状态机

目标：将 draft、确认、排队、分析和终止状态固化为可校验状态机。

工作内容：

- 实现 spec 中定义的允许状态迁移。
- 同一会话同一时间只允许一个活动分析。
- 确认请求、取消请求和完成事件保持幂等。
- 为每次状态变化写入有序事件。
- 支持 completed、partial、failed、cancelled 和 interrupted。
- 保存稳定错误码和恢复建议，不保存内部堆栈。

验收标准：

- 非法跨状态迁移被拒绝且不会污染任务记录。
- 重复确认不会创建两个分析任务。
- 任务状态和最后事件在事务中保持一致。

建议提交：`feat: 实现Web分析任务状态机`

### 任务 6：实现独立本地 Worker

目标：在 API 进程之外执行长时间报文分析。

工作内容：

- 实现 Windows `spawn` 兼容的 Worker 启动和停止。
- Worker 从 SQLite 原子领取 queued 任务，默认并发数为 1。
- 将应用服务进度转换为任务状态和进度事件。
- 定期写入 Worker 心跳和任务更新时间。
- 服务异常退出后将失去心跳的活动任务标记为 interrupted。
- 实现正常完成、部分完成、失败和报告持久化。
- 确保 API 和 Worker 使用相同配置但不传递密钥到任务表。

验收标准：

- 刷新或关闭浏览器不会中断任务。
- FastAPI 请求线程不执行完整诊断。
- Worker 重启后不会重复领取已完成任务。
- Worker 异常不会损坏已有分析产物。

建议提交：`feat: 增加Web后台分析Worker`

### 任务 7：实现安全取消和失败重试

目标：让用户能够取消长任务并基于原参数创建重试任务。

工作内容：

- 取消接口只写入取消请求，由 Worker 执行安全终止。
- 复用现有 Windows 和 macOS 子进程树终止能力。
- 取消后等待 TShark 和子进程确认退出，再标记 cancelled。
- 重试创建新的 analysis_id，保留原任务历史和关联关系。
- 明确哪些基础产物可以复用，复用前校验哈希和完整性。
- 取消、失败和 interrupted 任务均提供可执行恢复建议。

验收标准：

- Windows 和 macOS 中取消后无残留 TShark 子进程。
- 重复取消保持幂等。
- 重试不覆盖原报告、trace 和错误记录。

建议提交：`feat: 支持Web任务取消与重试`

## 6. 阶段四：实现 FastAPI 和 SSE

### 任务 8：搭建 FastAPI 应用与本机安全边界

目标：提供只监听本机的稳定 API 入口。

工作内容：

- 创建 FastAPI 应用工厂和依赖注入边界。
- 实现健康检查、版本信息和配置状态接口。
- 强制监听 `127.0.0.1`，校验 Host 和 Origin。
- 配置统一异常映射、请求 ID 和安全响应头。
- OpenAPI 在开发模式可用，生产本机模式按配置控制。
- API 日志过滤绝对路径、密钥、Payload 和完整模型消息。

验收标准：

- 非本机 Host 和不允许 Origin 被拒绝。
- API 错误只返回稳定错误结构。
- 配置状态只说明是否完成配置，不返回配置值和密钥。

建议提交：`feat: 搭建PacketMaster本地Web API`

### 任务 9：实现会话、消息和参数确认 API

目标：将现有 CLI 对话路由与参数补全能力提供给 Web。

工作内容：

- 实现会话创建、列表、详情和删除引用。
- 实现普通对话、诊断意图、短参数补充和方向修正。
- 将报文路径输入替换为 capture_id 绑定，不让模型接触路径。
- 返回待确认参数、缺失项、默认单位和方向说明。
- 实现修改和确认动作。
- 确认后创建 queued 分析任务。
- 会话删除不删除用户报文和共享分析产物。

验收标准：

- “TCP 是什么”进入普通对话。
- 完整任务可以一次确认，缺失任务可以逐项补充。
- 未确认任务不能进入 Worker 队列。
- 默认方向固定为下载。

建议提交：`feat: 提供Web会话与诊断确认API`

### 任务 10：实现分析、报告、指标和证据 API

目标：为任务详情和报告可视化提供有界数据。

工作内容：

- 实现分析状态、取消、重试和报告读取接口。
- 从现有聚合产物构建有界图表数据。
- 实现完整 TCP 流列表的服务端分页、排序和筛选。
- 实现证据类型、流和时间范围查询。
- 复用 MCP 证据字段白名单、页大小和 analysis_id 校验。
- 报告和指标接口明确覆盖、截断、单位和数据点压缩信息。

验收标准：

- 图表接口不返回完整逐包序列。
- 流和证据查询不能跨 analysis_id。
- 页大小、排序字段和筛选字段均有白名单。
- 完整报告与 CLI 使用同一 `DiagnosticReport`。

建议提交：`feat: 提供Web报告指标与证据API`

### 任务 11：实现可恢复 SSE 事件流

目标：向浏览器实时提供有序、可断线恢复的任务事件。

工作内容：

- 实现分析事件 SSE 端点。
- 使用持久化单调递增 event_id。
- 支持 `Last-Event-ID` 恢复。
- 定期发送轻量心跳，检测连接关闭。
- 过滤敏感字段和过大事件。
- 分析完成后发送终止事件并关闭或降频连接。
- 问答只推送状态和 ready 事件，不流式输出未校验模型文本。

验收标准：

- 断线重连不丢事件且不会重复改变任务状态。
- 多浏览器标签监听同一任务不会影响 Worker。
- SSE 不包含完整报告、证据、绝对路径和密钥。

建议提交：`feat: 实现Web分析进度事件流`

### 任务 12：实现诊断后持续问答 API

目标：围绕已完成任务提供证据约束问答。

工作内容：

- 将问题绑定当前 session_id 和 analysis_id。
- 复用现有问答 LangGraph 和有界 MCP 取证。
- 持久化问题、结构化回答、证据引用、限制和建议。
- 普通问题与报告问题继续使用统一对话路由。
- 回答失败时保留会话和已有报告。
- 对过期或缺失产物返回明确恢复建议。

验收标准：

- 问答不会重新执行基础 analyze。
- 每题最多两轮取证、每轮最多五个请求。
- 伪造引用和跨 analysis_id 请求被拒绝。
- 页面刷新后可恢复历史问答。

建议提交：`feat: 提供Web诊断持续问答API`

## 7. 阶段五：搭建 React 工作台

### 任务 13：创建前端工程和设计基础

目标：建立可测试、可构建、可由 Python 服务托管的 React 应用。

工作内容：

- 创建 React、TypeScript 和 Vite 工程。
- 配置路由、TanStack Query、ECharts 和 Lucide React。
- 建立颜色、间距、字体、边界、状态和响应式设计变量。
- 建立按钮、输入、对话框、标签、抽屉、状态和空状态基础组件。
- 配置前端 Lint、格式、组件测试和生产构建。
- 配置开发代理和生产静态资源路径。

验收标准：

- 开发模式可以连接本地 FastAPI。
- 生产构建可以由 PacketMaster 后端静态托管。
- 基础组件支持键盘、焦点和 loading/disabled 状态。
- 不使用卡片嵌套、装饰性渐变和营销式页面。

建议提交：`feat: 搭建PacketMaster React工作台`

### 任务 14：实现三栏工作台和会话管理

目标：实现桌面主布局、历史会话和页面恢复。

工作内容：

- 实现顶栏、左侧会话栏、中间主区和右侧上下文栏。
- 实现会话分页、搜索、状态分组、新建和切换。
- 实现左右栏折叠和窄屏抽屉。
- 实现空会话、加载、离线和服务错误状态。
- 页面刷新后恢复当前会话和任务。
- 浏览器本地只保存布局和草稿，不保存敏感数据。

验收标准：

- 常用桌面和笔记本视口无横向溢出。
- 切换会话时消息、任务和 analysis_id 不串用。
- 任务运行时切换会话不会中断后台任务。

建议提交：`feat: 实现Web会话工作台布局`

### 任务 15：实现对话、报文注册和参数确认

目标：完成从自然语言输入到分析确认的前端闭环。

工作内容：

- 实现消息列表、普通回答、补问、错误和系统状态。
- 实现自动增长输入框、发送、换行和输入限制。
- 实现报文路径注册对话框和最近报文选择。
- 右栏实时显示文件名、大小、标准/实际带宽和方向。
- 实现确认面板、默认单位说明、修改和开始分析。
- 防止重复提交、重复确认和无内容发送。

验收标准：

- 完整参数和分轮补充均可完成确认。
- 界面只显示脱敏文件名，不持久化真实路径。
- 键盘可以完成输入、注册、修改和确认流程。

建议提交：`feat: 实现Web对话与参数确认`

### 任务 16：实现实时进度、取消和重试体验

目标：让长时间分析过程持续可见、可恢复、可取消。

工作内容：

- 连接 SSE 并处理断线重连和 Last-Event-ID。
- 显示任务阶段、阶段说明、处理规模、耗时和状态。
- 在消息流和右栏同步展示进度。
- 实现取消确认、取消中、已取消和失败重试。
- 页面刷新后从服务端状态和事件恢复进度。
- 对重复和乱序事件进行幂等处理。

验收标准：

- 刷新页面后仍能看到当前进度。
- 取消按钮不会造成重复任务状态变化。
- 错误显示中文原因和可执行恢复动作。

建议提交：`feat: 实现Web实时分析进度`

## 8. 阶段六：报告、流与证据可视化

### 任务 17：实现诊断报告视图

目标：完整呈现当前结构化报告，不依赖额外模型转述。

工作内容：

- 展示带宽、达标率、方向、主因、置信度和覆盖完整性。
- 展示全部候选原因及支持、反向和缺失证据。
- 展示限制、排查步骤和优化建议。
- 实现从候选原因跳转到流和证据。
- 明确 partial、truncated 和 incomplete 状态。
- 提供 JSON 报告下载或本地位置查看命令。

验收标准：

- 报告内容与 CLI 和 report.json 一致。
- 长原因、流 ID 和证据文本不会溢出。
- 不能只用颜色区分置信度和状态。

建议提交：`feat: 实现Web诊断报告视图`

### 任务 18：实现指标图表和完整 TCP 流列表

目标：可视化吞吐、RTT、TCP 事件、窗口和流差异。

工作内容：

- 实现吞吐量时间序列和标准带宽参考线。
- 实现 RTT 分布和窗口变化。
- 实现重传、重复 ACK、乱序、零窗口和窗口满事件时间线。
- 实现标准、实际和报文测得吞吐对比。
- 实现完整流列表的分页、排序、筛选和流详情。
- 显示数据降采样、覆盖和截断信息。
- 图表提供文本摘要和可访问数据入口。

验收标准：

- 单图不超过约定数据点上限。
- 异常区间在降采样后仍可见。
- 流列表在大量流情况下保持分页和稳定布局。

建议提交：`feat: 增加TCP诊断指标可视化`

### 任务 19：实现证据浏览和诊断后问答

目标：完成从报告结论到具体证据、再到持续追问的闭环。

工作内容：

- 实现证据类型、流、时间范围筛选和分页。
- 展示允许的帧号、相对时间、流 ID、TCP 字段和事件类型。
- 从报告候选原因和回答引用定位证据。
- 展示回答正文、证据依据、限制和后续建议。
- 显示问答取证中和回答就绪状态。
- 切换任务时清理旧任务的临时筛选和回答状态。

验收标准：

- 页面不显示 Payload 和未允许字段。
- 回答中的引用可以解析到当前任务证据。
- 问答失败不会破坏报告和历史对话。

建议提交：`feat: 实现Web证据浏览与持续问答`

## 9. 阶段七：启动、打包与发布门禁

### 任务 20：实现 `packetmaster web` 启动命令

目标：在 Windows 和 macOS 通过一个命令启动本地工作台。

工作内容：

- 注册 `packetmaster web` 命令。
- 启动 FastAPI、Worker 和前端静态资源服务。
- 默认选择可用本机端口并输出访问 URL。
- 服务就绪后打开默认浏览器。
- 支持 Ctrl+C 安全停止 API 和 Worker。
- 处理端口占用、前端资源缺失和数据库迁移失败。

验收标准：

- Windows 和 macOS 均可启动、访问和安全退出。
- 不使用仅适用于 Unix 的进程和信号行为。
- CLI diagnose 和 chat 不受 Web 依赖影响。

建议提交：`feat: 增加PacketMaster Web启动命令`

### 任务 21：完善依赖、构建和安装流程

目标：让 Python 包和前端产物可以稳定安装与发布。

工作内容：

- 将 Web 后端依赖放入明确的可选依赖组或正式运行依赖。
- 固定前端 Node 和包管理器版本范围。
- 配置前端构建产物进入 Python 包。
- 增加从干净环境安装后的资源存在性测试。
- 更新 requirements、README 和 Windows/macOS 安装说明。
- 明确开发模式和生产模式启动方法。

验收标准：

- 干净虚拟环境安装后无需源码目录即可启动 Web。
- 前端静态资源、数据库迁移和 Prompt 均包含在发布包中。
- CLI 用户无需安装前端开发工具即可使用已构建 Web。

建议提交：`build: 完善Web工作台安装与打包`

## 10. 建议实施批次

为降低单次变更风险，建议按照以下批次执行：

### 批次一：后端基础

- 任务 1 至任务 4。
- 完成共享应用服务、领域契约、SQLite 和报文注册。
- 此时不创建前端页面。

### 批次二：异步分析 API

- 任务 5 至任务 12。
- 完成状态机、Worker、取消、FastAPI、SSE、报告和问答 API。
- 使用 API 集成测试验证完整流程。

### 批次三：React 对话工作台

- 任务 13 至任务 16。
- 完成主布局、会话、对话、确认和实时进度。

### 批次四：可视化闭环

- 任务 17 至任务 19。
- 完成报告、指标、流、证据和持续问答。

### 批次五：交付

- 任务 20 至任务 22。
- 完成启动命令、打包、文档和发布门禁。

## 11. 完成定义

只有同时满足以下条件，Web 对话界面 MVP 才算完成：

- spec 和本 plan 的验收标准全部满足；
- CLI 与 Web 共用诊断核心且行为一致；
- 浏览器刷新和服务短暂重启不会丢失已持久化任务；
- 长时间分析不阻塞 API，取消无残留子进程；
- 报告、图表、完整流列表、证据和持续问答形成可用闭环；
- 原始报文、Payload、密钥和绝对路径边界通过自动化验证；
- Windows 正式门禁和 macOS 兼容门禁通过；
- 使用文档、安装文档和现阶段功能说明同步更新；
- 所有相关变更使用中文 Git 提交信息提交。
